# ขั้นตอนรีวิวการเปลี่ยนแปลง

ใช้เอกสารนี้เมื่อรีวิว diff, PR, แผนงาน หรือข้อเสนอปรับโครงสร้าง

`AGENTS.md` ครอบกฎการทำงานประจำ เอกสารนี้ครอบวิธีรีวิวเมื่อมีของให้ตรวจ

## จุดยืน

อ่านของจริง ไม่ใช่คำอธิบายของผู้เขียน อ่าน diff, โค้ดรอบข้าง และคำอธิบายของ PR แยกจากกัน

ขอบเขตไม่จบที่ diff ให้ไล่ call path ทั้ง repo

รายงานแต่ละข้อครั้งเดียว เรียงตามความรุนแรง บอกว่าต้องแก้อะไร ทำไม และหลักฐานคืออะไร

## ขั้นที่ 1 เจตนา

บอกเป้าหมายของงานในประโยคเดียว ถ้าเขียนไม่ได้ แปลว่าข้อเสนอยังไม่ชัด ให้หยุดแล้วรายงานว่าขาดอะไร

ตอบคำถามนี้ก่อนอย่างอื่น

- สิ่งนี้ควรมีอยู่จริงหรือไม่ ปัญหานี้เกิดขึ้นจริงและรับน้ำหนักอยู่จริงหรือเปล่า
- มีอะไรในโค้ดเดิมที่ทำหน้าที่นี้อยู่แล้วหรือไม่
- มีทางที่เล็กกว่าซึ่งได้ผลเก้าสิบเปอร์เซ็นต์ด้วยความเสี่ยงสิบบเปอร์เซ็นต์หรือไม่
- มีชั้นอื่นที่เหมาะกว่าไหม เช่น ตั้งค่าที่ config แทนการแก้โค้ด หรือใช้สิ่งที่ framework มีอยู่แล้ว

ถ้ามีทางที่ดีกว่า ให้ระบุทางนั้นก่อนตรวจทีละบรรทัด ข้อนี้มีค่าที่สุดในรายงาน

**เสร็จเมื่อ** เขียนเป้าหมายได้หนึ่งประโยค และระบุทางเลือกที่ชนะหรือระบุว่าไม่มีทางใดชนะ

ข้ามขั้นนี้ได้เฉพาะเมื่อผู้สั่งบอกชัดว่าไม่ต้องตั้งคำถามเรื่องขอบเขต

## ขั้นที่ 2 ไล่ code path

ทุกพฤติกรรมที่ของชิ้นนี้อ้าง ให้ไล่จากทางเข้าถึงทางออกในโค้ดจริง

ค้นชื่อ symbol ที่เปลี่ยนทุกตัวก่อน แล้วตามไปทุกจุดที่เรียกใช้ รวมถึง caller, test และ config key

ไล่ตามเส้นนี้ และอ่านโค้ดทั้งสองข้างของ diff

- ทางเข้า แล้วจุดที่เรียกใช้ แล้วสาขาที่ถูกเลือก แล้ว state ที่เปลี่ยน แล้วจุดจบหรือ side effect
- บั๊กซ่อนอยู่ที่รอยต่อระหว่างส่วน
- บันทึกทุกจุดที่ทำให้ประหลาดใจ สาขาที่ไม่คาดคิด, โค้ดตายที่ถูกเรียก, state ที่ไม่รู้ว่ามีอยู่ จุดพวกนี้คือสัญญาณ

ถ้าเป็นแผนงานหรือเอกสารออกแบบ ให้ไล่ลำดับที่เสนอเทียบกับระบบที่มีอยู่จริง ระบุว่ามันแตะของจริงตรงไหน และสมมติอะไรที่ไม่จริงไว้

**เสร็จเมื่อ** ทุกพฤติกรรมที่อ้างมีเส้นทางจากทางเข้าถึงทางออกที่ระบุชื่อได้ และอ่านโค้ดทั้งสองข้างของ diff แล้ว คำอ้างที่ไล่เส้นทางไม่ได้ให้สถานะ unchecked

## ขั้นที่ 3 ตรวจว่าทำอย่างที่อ้างจริงหรือไม่

ทุกคำอ้างในของชิ้นนี้ ต้องตอบสี่ข้อนี้แล้วให้สถานะเป็น held, refuted หรือ unchecked

**เส้นทางที่ไล่มาให้พฤติกรรมนั้นจริงหรือไม่** ไล่จากคำอ้าง ไปเส้นทาง ไปจุดสังเกตที่ตัดสินผล

**ข้อมูลหรือ state แบบใดทำให้พัง** ครอบ edge case, ผู้เรียกพร้อมกัน, เส้นทาง error, ความล้มเหลวบางส่วน, การลองซ้ำ, ค่าว่าง, null, unicode, ข้อมูลขนาดใหญ่, และสมมติฐานเรื่องลำดับ

**มันเปลี่ยนอะไรโดยไม่บอก** ทั้ง performance, ความหมายของ error, observability, สัญญาเดิมของ caller อื่น, รูปแบบที่เขียนลงดิสก์หรือส่งบนเครือข่าย

**เทสต์แตะเส้นทางที่ไล่มาหรือไม่** หรือเทสต์ผ่านเพราะข้ามเส้นทางนั้นไป ระวัง mock ที่กลบปัญหา, assert บน state กลางทาง, และเทสต์ที่ครอบเฉพาะทางสำเร็จ

**เสร็จเมื่อ** ทุกคำอ้างมีสถานะพร้อมหลักฐานหรือระบุเส้นทางที่ขาด

## ขั้นที่ 4 รายงาน

เขียนหนึ่งหัวข้อต่อหนึ่งสิ่งที่พบ เรียงจาก blocker แล้ว major แล้ว nit

- **blocker** ผิดหรือไม่ปลอดภัยถ้าปล่อยตามที่เขียน
- **major** ทำงานได้แต่ทำให้ caller เสีย, ผิดสัญญา, หรือพังเมื่อเจอโหลดจริง
- **nit** เรื่องรูปแบบ และเขียนเฉพาะเมื่อมีคนจะลงมือแก้

ปัญหาเชิงโครงสร้างจากขั้นที่ 1 หรือ 2 ให้ขึ้นก่อนเสมอ

แต่ละข้อมีสี่ส่วน

**สิ่งที่พบ** ประโยคเดียว เจาะจง อ้าง `file:line`
**ทำไมสำคัญ** บอกผลที่เกิดขึ้น ไม่ใช่บอกหลักการ
**หลักฐาน** ขั้นตอนหรือข้อมูลที่ทำให้เห็น พร้อมสถานะของคำอ้าง ถ้าไม่ได้ไล่จริงให้เขียนว่า asserted
**ข้อเสนอ** เจาะจง ทำน้อยที่สุด

ปิดด้วยหนึ่งบรรทัด บอกว่า ship, fix-then-ship, rework หรือ reject พร้อมเหตุผลเดียวที่ใหญ่ที่สุด และตอบคำถามจากขั้นที่ 1 ว่าทางเลือกที่ชนะคืออะไร หรือไม่มีทางใดชนะ

**เสร็จเมื่อ** ทุกคำอ้างที่ refuted หรือ unchecked มีหัวข้อของตัวเอง และบรรทัดปิดระบุเหตุผลที่ใหญ่ที่สุด

ถ้าตรวจแล้วไม่พบอะไร ให้รายงานว่าไล่อะไรไปบ้าง ตรวจอะไร และอ่านอะไรยังไม่ได้อ่าน

## เรื่องที่เอกสารนี้ไม่ครอบ

ความสอดคล้องกับมาตรฐานของ repo และ spec ให้ส่งต่อให้ code-review เอกสารนี้ตอบคำถามว่าของชิ้นนี้ควรมีอยู่ไหม และทำอย่างที่อ้างจริงหรือไม่

การตรวจคุณภาพเชิงลึกด้านลอจิก ความปลอดภัย และโหลด อยู่นอกขอบเขตของที่นี่
